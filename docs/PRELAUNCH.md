## 1. Invitations and account creation

### 1.1 How long an invite link actually lives — `UNVERIFIED` (external setting)

There are **two different clocks**, and they are not the same:

| Clock                                   | Value                                                                  | Where it lives                     | Authoritative?                                 |
| --------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| Our `agency_invitations.expires_at` row | **7 days** (`INVITE_TTL_DAYS`)                                         | `src/lib/invitations.functions.ts` | No — our bookkeeping for the pending list only |
| The invite **link's** lifetime          | **Supabase project setting "Email OTP expiration", 1 hour by default** | Supabase Auth project settings     | **Yes — the link dies on this clock**          |

Verified from Supabase's own docs (Passwordless email sign-in → With OTP):

> "By default, a user can only request an OTP once every 60 seconds, and they
> expire after 1 hour. This is configurable via **Authentication > Sign In /
> Providers > Auth Providers > Email > Email OTP expiration**."
>
> "**Caution:** The **Email OTP Expiration** setting also governs the validity of
> Magic Links and other email links, including confirmation, password recovery,
> email change, and **invitation** links."

And: an expiry longer than 86,400 s (one day) "is strongly discouraged and can
only be set via the Management API."

**Therefore:** the default is **1 hour**, not 7 days. Our 7-day row does **not**
extend the link. The UI now states the 1-hour default and points at the project
setting instead of promising 7 days.

- [ ] Confirm the project's **Email OTP expiration** value in the Supabase
      dashboard and decide if 1 hour is acceptable for onboarding (an admin who
      shares a link by WhatsApp after an hour is sending a dead link).
- [ ] If a longer window is needed, change the project setting (keep it
      ≤ 86,400 s) and update `INVITE_LINK_LIFETIME_LABEL` in
      `src/lib/invitations.functions.ts` so the copy stays true.
- [ ] `INVITE_TTL_DAYS` (7) must stay **≥** the link's real lifetime, so a row
      never stays "pending" after its link is already dead. If the project setting
      is raised past 7 days, raise this too.

### 1.2 The first admin's link has no invitation row — partially mitigated

`provisionAgency` creates the first admin via `generateLink`, but — unlike
`inviteTeamMember` — it does **not** write an `agency_invitations` row (there is
no row to write: the invitation table keys off an agency admin who does not exist
yet). Consequences:

- The team screen cannot list, resend, or revoke the first admin's invitation.
- `DONE` (super admin) The platform **agency detail page** now offers
  **Re-issue link** for a still-pending agency admin, which issues a fresh link
  and shows it to copy. This is the recovery path for a first admin whose link
  expired before it was used.
  - Scope: super admin only; target must belong to the agency, hold the
    `agency_admin` role, and be `pending`.
- `TODO` Revocation of a first-admin link is still not possible (a generated
  link cannot be revoked without accepting it or resending over it). Acceptable
  for v1; re-issue covers the real-world case.

### 1.3 Email delivery — `UNVERIFIED` (no transport configured here)

`emailConfigured()` is true only when `SMTP_HOST` or `RESEND_API_KEY` is set.
Both are **unset** in this environment, so every invite path is copy-paste only
and the "email was sent" branch has **never been exercised** here.

- [ ] Set `SMTP_HOST`/`RESEND_API_KEY` (by name) and test one real invite and one

## 3. Database migrations not yet applied

Written locally, **not applied** to the live project. Applying needs explicit
sign-off.

- `drizzle/migrations/0016_no_subscription_uses_free_plan.sql` — makes an agency
  with no `subscriptions` row behave as the **Free** plan limits (5 properties,
  20 leads, 2 team members, 100 WhatsApp messages, 50 AI requests, 1 GB storage)
  instead of "unlimited".
  - **Operational risk:** agencies created _before_ this migration have no
    subscription row. Once applied they become Free-capped, so any such agency
    already above those numbers will start failing inserts that count against the
    metric. Grandfather existing agencies (backfill a subscription) **before**
    applying.
  - Canceled/expired subscriptions still keep the plan they were on; reverting
    **canceled** subscriptions to Free is out of scope and not done here.

### 3.1 Which migrations are pending is not recorded reliably

Three things that could track it, and what each one actually holds:

| Source                                         | What it holds                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------------- |
| `drizzle/migrations/meta/_journal.json`        | only `0000`–`0001`; it stops long before the chain ends                    |
| `scripts/apply-migrations.mjs`                 | applies the files and commits; it writes **no** tracking row               |
| `supabase_migrations.schema_migrations` (live) | as recorded on 2026-10-13, a single row: `0009_lock_down_function_execute` |

So "pending" cannot be computed from the repo, and the recording table is not
the whole story either. Before applying anything, check the live project with a
read-only query and treat that as the source of truth.

Recorded, but **not re-verified here**: `0010`–`0013`
(`docs/IMPLEMENTATION_STATUS.md` — otherwise out of date, it cites a
122-section test run where the current battery is 159) and `0016` (this file).

`drizzle/migrations/` holds `0000`–`0016`; the next free number is **0017**.

### 3.2 How to apply, when the time comes

```bash
node scripts/apply-migrations.mjs --dry-run --from 0010   # list, no connection
node scripts/apply-migrations.mjs --from 0010             # apply that batch
```

- `--from` starts at the first number that has not been applied, so an
  already-applied migration is never replayed against real data.
- The whole batch runs in **one transaction** and rolls back on any error, so a
  failure cannot leave the schema half-migrated.
- Never start at `0000`: those are applied in substance, and a replay risks
  re-touching data.
- `drizzle-kit migrate` cannot be used at all — its journal stops at `0001`.
- Grandfather existing agencies before `0016` (see above), and get explicit
  sign-off before any of this reaches the live project.

## 6. Installable app (PWA)

Shipped in this pass. What is in place:

- `public/manifest.webmanifest` — standalone display, theme `#095B41`, four
  icons (two `any`, two `maskable`).
- `public/sw.js` — caches **static assets only**: `/assets/*` (cache-first;
  those URLs are content-hashed) and `/manifest.webmanifest`, `/favicon.ico`,
  `/robots.txt`, `/icons/*` (served from cache, revalidated on each use). It
  never caches HTML, `/api/*` or server-function responses: every page is
  tenant- and permission-scoped, so a shared cache entry would serve one
  agency's data to the next session.
- Registration is **production-only** (`src/components/pwa/useServiceWorker.ts`).
  In dev the hook actively unregisters a leftover worker and deletes
  `estateos-*` caches, so a previewed build can never shadow the dev server.
- Install UI: Chromium/Edge get the real `beforeinstallprompt` banner. iOS
  Safari has no such API, so it gets a "Tap Share, then Add to Home Screen"
  instruction instead. Dismissal is remembered under
  `estateos:pwa-install-dismissed`.

Operating it:

- Bump `CACHE_VERSION` in `public/sw.js` when a non-hashed file changes. A
  250-entry oldest-first cap is the backstop if a bump is forgotten.
- No `skipWaiting()`: a new worker takes over on the next full restart, so
  activation cannot delete cache entries the open page still needs.
- Emergency unregister procedure: `docs/DEPLOY.md`.
